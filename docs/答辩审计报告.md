## 3. 必须保留为「承认」的清单

这些不建议为了答辩硬修成「假完整」。改了要么违反题目约束，要么把规则说圆了反而像掩饰。

1. **不接真实支付、无网关回调、无对账文件。** 模拟成功/失败是按钮，不是通道。
2. **完成订单没有物流/签收。** 状态机里的履约节点，不是配送系统。
3. **店员不能储值充值。** 资金入口只给管理员，这是范围选择。
4. **支付成功后退款不退券。** 规则如此，不是漏做。
5. **不用 Celery / Redis。** 超时靠访问扫描 + 管理命令，须主动报扫描点。
6. **「累计积分」是净值。** 退款会扣、可能降级。
7. **模拟支付失败不关单。** 允许重试；不要说失败即取消。
8. **没有高并发压测。** 行锁是正确做法，不是已验证的秒杀方案。
9. **演示账号写在 README。** 毕业设计惯例，声明不用于生产。
10. **截图不是 1920。** 可重录，不必改业务代码。
11. **git 尚无 commit。** 因本机身份未配置；不要假装有迭代历史。
12. **Jazzmin Select2 补丁。** 升级主题可能再吞动作按钮。
13. **储值不够不会拒单。** 剩余走模拟网关。不要用「余额不足拒绝支付」当能答。

**必须承认项合计：13。**

## 4. 答辩话术建议（每个「必须承认」一句）

1. 真实支付：「题目不允许接真实网关。我实现的是状态机和分账：储值流水 + 模拟网关流水，成功才发积分。」
2. 无物流：「已完成只表示店内履约打标，配送不在本系统范围。」
3. 店员不充值：「储值是资金入口，演示里只给管理员；店员负责收银和发券。」
4. 退款不退券：「取消待支付会退券；支付成功后退款视为已经享受优惠，券不退。」
5. 无 Celery：「按任务书不加独立调度。超时 30 分钟，进入订单、结算、支付、会员中心或看板时扫描，也提供管理命令。」
6. 净累计：「累计积分按净值记账，退款扣回该单已发积分并重新套档，可能从金卡降到银卡。业务规则文档写了。」
7. 支付失败：「失败只记一条失败支付记录，订单仍待支付，方便现场演示重试。」
8. 无压测：「预扣库存和 `select_for_update` 是为正确性，不是为压测指标。演示数据量下足够。」
9. 明文密码：「README 里的是种子演示账号，论文安全节会写明仅本地演示。」
10. 截图分辨率：「仓库预置图便于插图草稿，正式打印用 1920 最大化重录。」
11. 无 git 提交：「代码已在暂存区，本机 git 未配提交者信息，我按规则没有改 git config。」
12. Select2：「Jazzmin 的 Select2 曾把动作下拉撑空，我用自定义 JS 修过，升级主题要回归。」
13. 储值不足：「支付不会因为储值不够失败。储值能扣多少扣多少，剩余走模拟网关，和现场勾选“优先储值”的展示一致。」

补充（手册能答过满、要改口）：

- 超库存：「加购阶段不锁死库存，**提交订单**时预扣，不够会提示并保持待支付无法生成。」
- 并发领券：「服务层锁的是券模板行；库里没有唯一约束。演示双击不容易超，我不会把它写成已解决并发。」
- 超时测试：「有用例证明超时后再支付会被拒绝并取消；没有两线程同时点支付的压测。」

开场仍建议用手册那句：复杂度在订单状态机，后台不能手改状态绕过服务。
