## 1. 选题背景

中小型花店日常同时面对三类事务：前台选花下单、会员积分与储值、店内备花与收银。通用电商后台过重，表格记账又无法把「库存、优惠券、等级折扣、储值抵扣」算在同一笔订单上。本课题以单体 Web 系统把上述事务收成一条可演示、可核对流水的闭环，供本科毕业设计使用。

系统品牌名 **花间集**，口号 **以花为集，以客为心**。它不是上线运营的电商，不对接真实支付与第三方物流。

## 2. 建设目标

1. 会员能在前台完成：浏览花市 → 加购 → 结算（等级折扣、优惠券、储值）→ 模拟支付 → 查看积分 / 储值流水。
2. 店员能在后台完成：看库存、收银相关操作、发券、发货或自提核销、审核取消申请。
3. 管理员能完成：账号与规则管理、后台储值调账、整单退款、经营看板。
4. 每一笔已支付订单都能在库存、储值、积分、等级、支付流水和看板上对上，而不是各写各的账。

## 3. 角色与范围

| 角色 | 入口 | 能做 | 不能做 |
| --- | --- | --- | --- |
| 会员 | 前台 | 购物、改资料、改密、领券、自助充值、申请取消、确认签收 | 进 `/admin/`、自己点「我已自提」、对已发货单直接退款 |
| 店员 | Admin + 看板 | 商品与库存、发放优惠券、支付 / 发货 / 自提核销、审核取消 | 管用户、建券模板、后台充值、对已发货单直接退款 |
| 管理员 | Admin + 看板 | 全量权限，含用户、等级规则、券模板、调账、直接退款 | — |

**范围内**：会员、等级、积分、储值、商品、购物车、模拟支付、店内履约、优惠券、RBAC、ECharts 看板。  
**范围外**：真实支付网关、快递公司对接、售后退货物流、多门店、微服务、消息队列。

## 4. 技术选型

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 架构 | 单体 Django MVT | 导师范围要求；一人可维护；业务规则适合放在服务层 |
| 前端 | Templates + 自定义 CSS | Windows 无 Node 构建也能跑；视觉用设计 Token 控制 |
| 后台 | Admin + jazzmin | 店员桌面端够用，不必再做一套管理 SPA |
| 数据库 | MySQL 8.0 + ORM | 事务与行锁能支撑库存预扣；测试改 SQLite |
| 图表 | 本地 ECharts 6.0 | 答辩机房可能断网 |
| 明确不做 | DRF / Vue / Celery / Redis / Docker | 超出题目与导师清单，也不是本系统的瓶颈 |

从第一天使用自定义用户 `accounts.User`（`AUTH_USER_MODEL`），避免中途改用户表。

## 5. 模块划分

| 应用 | 职责 | 核心文件 |
| --- | --- | --- |
| `accounts` | 用户、角色、登录注册改密、权限组 | `models.py` `rbac.py` |
| `members` | 档案、等级、积分、储值、自助充值 | `services.py` |
| `products` | 分类、商品、花市检索 | `views.py` |
| `orders` | 购物车、下单、支付、履约、退款 | `services.py` |
| `marketing` | 券模板、领取、核销、过期 | `services.py` |
| `dashboard` | KPI、六张图、店务待办 | `services.py` |
| `core` | 首页、会员装饰器、`seed_demo` | `management/commands/seed_demo.py` |

调用关系可以概括为：

**花市加购 → `create_order_from_cart`（预扣库存、核销券）→ `pay_order`（扣储值、记网关流水、发积分、升降级）→ `ship_order` / `pickup_order` → 看板统计实收。**

取消待支付或超时：回库存、退券。支付成功后再退款：回库存、回储值、扣积分，**不退券**。

## 6. 设计要点（论文可写成创新或关键实现）

1. **订单金额拆分**：商品合计、等级折扣、券抵扣、应付、储值实付、网关实付分字段保存，看板只汇总实收，不另做一套账。
2. **库存与状态机**：待支付即预扣；状态变更写 `OrderStatusLog`；后台订单状态只读，支付 / 退款走 Admin 动作进入服务函数。
3. **积分净值套档**：累计积分随退款扣回，等级可能下降，避免「退了货还留着钻石」。
4. **两条资金入口**：会员自助充值走独立表 `StoreRecharge`，成功后才写入储值流水，避免把充值算进花市销售额。
5. **店内履约而不是物流系统**：配送与自提只增加必要状态和地址快照，不模拟运单、轨迹、货到付款。
6. **访问触发扫描**：待支付超时、券过期不依赖 Celery，进入首页 / 花市 / 订单 / 看板时扫描，并保留管理命令。

## 7. 演示数据

`python manage.py seed_demo` 会准备：

- 账号：`admin`、`staff`、五名会员（覆盖普通到钻石）
- 商品：13 款（花束 / 绿植 / 礼盒），图片在 `media/products/`
- 优惠券模板与领取记录
- 近两周带「演示数据」标记的订单，供看板出曲线
- `demo_member` 购物车里预置一件商品

重建订单：`python manage.py seed_demo --force`。

## 8. 评价标准（自检）

达到本科优秀毕业设计的演示标准，本项目按下面几条自检：

- 一条完整业务链可以在答辩现场走完，并且后台流水、库存、看板同时变化。
- 三角色权限可当场切换验证，店员看不到用户管理和直接退款。
- 有种子数据、有自动化测试、有与实现一致的文档。
- 能清楚说出「模拟」边界：支付、充值、配送都是店内语义，不是第三方服务。
