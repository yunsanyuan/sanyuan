## 0. 多视角总评（先读）

| 角色 | 结论 |
| --- | --- |
| 产品经理 | 两个能力都补「演示闭环缺口」，不要做成物流公司或钱包产品。配送是店内履约节点，充值是会员自助入金。 |
| Django 架构师 | 状态机继续收口 `services.py`；Admin 状态只读；不新增应用也能做，但充值不要塞进 `Order`，以免看板把充值算成花市销售额。 |
| 数据库设计师 | 配送用订单上的履约快照 + 一个状态值；充值单独一张待入账单。少表、可迁移、兼容已有演示单。 |
| 后端 | 复用 `pay_order` 的「失败不关单 / 成功才入账」、`recharge()`、`select_for_update`、`OrderStatusLog`、访问触发扫描。 |
| 前端 UI/UX | 会员端只加「签收」「去充值」两条主路径；后台只加「发货 / 代签收」动作。沿用森绿 Token，不新开视觉体系。 |
| 测试 | 先锁状态迁移和越权，再补看板口径（`shipped` 必须算已收款）。 |
| 答辩老师 | 做完后第 2 条「无物流」和第 3 条「只有管理员能充」会改口，但**不能**改口成真实物流或真实支付。 |

**设计拍板（信息不足时的默认，扩大范围已标注）：**

1. **不在「已完成」之后再挂一段配送。** 把现有 `completed` 改义为「已签收」，在 `paid` 与 `completed` 之间插入 `shipped`（配送中）。否则订单已显示「已完成」却还在路上，答辩会被追问状态语义。  
   **扩大范围**：改写现有订单状态机含义，需改 `complete_order`、看板 `PAID_STATUSES`、种子数据、文档。
2. **提供自提捷径**（已支付 → 已签收，不经配送中）。花店现场常见。  
   **扩大范围**：多一种履约方式，结算页多一组字段。
3. **充值不进商品订单表。** 新建 `StoreRecharge`，成功后只调用现有 `recharge()` 写 `StoreRecord`。
4. **充值不赠积分、不做档位赠金。** 避免和「累计积分净值 / 消费积分」缠在一起。
5. **店员仍不能后台充值**，也不能替会员点前台充值。资金入口 = 管理员后台调整 ∪ 会员自助模拟网关。

## 1. 需求理解与范围边界

### 1.1 要做

**A. 店内配送与签收（模拟履约，不是物流系统）**

- 结算时选择履约方式：配送 / 自提。
- 配送单：收货人、电话、地址写入**本单快照**（改资料不影响历史单）。
- 已支付 + 配送 → 店员「发货」→ 配送中；会员「确认签收」（店员可代签）→ 已签收。
- 已支付 + 自提 → 店员「已自提」或会员到店后由店员代点 → 已签收。
- 模拟运单号：本系统生成（如 `FLW` + 订单号后段），不调第三方。
- 状态变迁继续写 `OrderStatusLog`。
- 看板待办增加「待发货」。

**B. 会员自助储值（模拟入金）**

- 会员中心 / 积分与储值页进入「储值充值」。
- 选金额 → 生成待入账单 → 模拟支付成功才加余额；失败仍待入账，可重试。
- 成功走现有 `members.services.recharge()`，流水类型仍是 `StoreRecord.Kind.RECHARGE`。
- 待入账 30 分钟超时关闭（不入账），扫描点并入现有访问扫描，不用 Celery。
- 管理员后台充值保留，口径改为「人工调账 / 演示补余额」。

### 1.2 不做

- 真实支付、回调、对账文件、微信/支付宝 SDK。
- 第三方物流 API、地图轨迹、电子面单、运费计价引擎。
- 售后工单、部分退款、拒收原返、破损理赔。
- 多地址簿、小区驿站、定时达、冷链、配送员账号。
- 充值赠积分、充值折扣券、充值套餐营销。
- 店员代会员充值、会员给他人充值。
- 充值单退款（资金原路退）。管理员仍可用现有人工调整流水纠错。
- DRF / Vue / React / Redis / Docker / Celery。

### 1.3 明确不改的承认项

真实支付、无 Celery、净累计积分、支付失败不关单、无压测、README 演示密码、截图分辨率、git 身份、Select2 补丁、储值不够走网关补足——本方案都不推翻。

## 2. 业务流程与状态机

### 2.1 订单履约（推荐）

```
待支付 ──支付成功──► 已支付 ──发货──► 配送中 ──签收──► 已签收
   │                    │                              ▲
   │                    └────自提核销──────────────────┘
   └──取消 / 超时──► 已取消

已支付 / 配送中 / 已签收 ──整单退款──► 已退款
```

| 现码值 | 现中文 | 新中文 | 含义 |
| --- | --- | --- | --- |
| `pending` | 待支付 | 不变 | 已预扣库存，未收款 |
| `paid` | 已支付 | 不变 | 已收款；配送单待发货，自提单待核销 |
| `shipped` | （新） | 配送中 | 仅配送单；已出店 |
| `completed` | 已完成 | **已签收** | 履约终点（签收或自提核销） |
| `cancelled` | 已取消 | 不变 | 仅待支付可入 |
| `refunded` | 已退款 | 不变 | 回库存、回储值、扣积分、不退券 |

**自提不进入 `shipped`。** 避免「自提却配送中」。

服务函数（均 `transaction.atomic` + `select_for_update` 订单行）：

| 函数 | 从 | 到 | 谁调 | 备注 |
| --- | --- | --- | --- | --- |
| `pay_order` | pending | paid | 会员 / 店员收银 | 现逻辑不变 |
| `ship_order` | paid 且 method=delivery | shipped | 店员 / 管理员 | 写 `shipped_at`、生成运单号 |
| `receive_order` | shipped | completed | 会员本人；店员可代签 | 写 `received_at` |
| `pickup_order` | paid 且 method=pickup | completed | 店员（主）；会员端可不开放自提自助核销 | 防止会员在店外点「我已自提」 |
| `complete_order` | — | — | **废止对外语义** | 内部改为调用 `receive_order` 或 `pickup_order`，避免两套入口 |
| `cancel_order` | pending | cancelled | 不变 | |
| `refund_order` | paid / shipped / completed | refunded | 仅管理员 | 配送中退款：库存仍按现规则回补；不模拟回库物流 |

会员端不提供「标记已完成」。现 Admin「标记已完成」拆成「发货」「确认签收 / 自提核销」。

### 2.2 下单时采集履约信息

结算 POST 增加：

- `fulfillment`：`delivery` | `pickup`（默认 `delivery`）
- `receiver_name` / `receiver_phone` / `address`：配送必填；自提可空，展示「到店自提 · 花间集」

预填：`Member.real_name`、`User.phone`、新增的 `Member.default_address`（可空）。  
**扩大范围**：会员资料多一个默认地址字段。

创建订单时写入订单快照。支付后不可改地址（与「已预扣后明细只读」同一口径：要改先取消未支付单；已支付只能退款重下）。  
**不确定**：已支付未发货是否允许改地址。默认不允许，避免店员口头改单无审计。

### 2.3 自助充值状态机

```
待入账 ──模拟成功──► 已入账 ──► recharge() 写储值流水
   │
   ├──模拟失败──► 仍待入账（可重试）
   └──超时 30 分钟──► 已关闭（不入账）
```

刻意对齐订单支付：失败不关单、成功才动余额、超时单独关。  
同一会员**最多一张待入账**（并发双提交时第二张 `IntegrityError` → 业务错「请先完成或等待上一笔充值」）。

充值**不发积分、不套等级**。等级只跟消费净值走。

## 3. 数据模型与迁移影响

### 3.1 订单：加字段，加一个状态值

`apps/orders/models.py` · `Order`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `status` | 现 CharField | choices 增加 `shipped`；`completed` 的 label 改为「已签收」 |
| `fulfillment` | CharField | `delivery` / `pickup`，默认 `delivery` |
| `receiver_name` | CharField(32, blank) | 快照 |
| `receiver_phone` | CharField(20, blank) | 快照 |
| `address` | CharField(200, blank) | 快照 |
| `tracking_no` | CharField(32, blank) | 发货时生成 |
| `shipped_at` | DateTimeField null | |
| `received_at` | DateTimeField null | 签收或自提核销 |

**不新建物流公司表、配送员表、轨迹表。** 发货备注可写在本次 `OrderStatusLog.remark`。

索引：已有 `order_status_idx`。建议加 `order_fulfillment_idx`（待发货列表：`status=paid, fulfillment=delivery`）。非必须，演示数据量下可后补。

自定义权限建议：

- `orders.ship_order` 发货
- `orders.receive_order` 代签收 / 自提核销  

店员拥有二者；会员走前台视图，不靠 Admin 权限。

### 3.2 会员：默认地址

`Member.default_address` CharField(200, blank=True)。  
资料页、结算预填共用。

### 3.3 充值单（新表，不挂 `Order`）

`StoreRecharge` · 建议 `db_table = member_store_recharge`

| 字段 | 说明 |
| --- | --- |
| `recharge_no` | 唯一，`RC` + 时间 + 随机，仿 `gen_order_no` |
| `member` | FK |
| `amount` | Decimal(12,2)，> 0 |
| `status` | `pending` / `success` / `closed` |
| `hold_key` | 可空；待入账 = `member_id`，成功/关闭 = NULL。唯一约束防双待入账（同领券 `hold_key`） |
| `trade_no` | 模拟网关流水号，可空 |
| `paid_at` | 成功时间 |
| `created_by` | 会员自己 |
| `remark` | |

**不把 `PaymentRecord.order` 改成可空。** 那会让支付流水和商品订单 1:N 语义破裂，属于扩大范围。充值成功/失败记在本表字段即可；余额变动仍只认 `StoreRecord`。

### 3.4 迁移与历史数据

一次迁移建议包含：订单新字段、`shipped` 不需要 Alter 枚举以外的数据变换（CharField）、会员地址、新表、`hold_key` 约束。

历史订单：

| 现状 | 迁移策略 |
| --- | --- |
| `completed` 且无履约字段 | `fulfillment=pickup`，`received_at=paid_at 或 updated_at`，视为已自提核销 |
| `paid` 未完成 | `fulfillment=delivery`，地址空；店员发货前须补地址，否则 `ship_order` 拒绝 |
| `refunded` / `cancelled` | 履约字段空即可 |

`seed_demo` 需改（实施阶段，非本文件）：14 天演示单应出现「待发货 / 配送中 / 已签收 / 自提」各至少 1 笔，否则投屏状态饼图仍像旧系统。

**不确定**：现网 MySQL 是否已有人手改出来的脏状态。代码层状态只读后按理只有服务层写入。

### 3.5 看板口径（必改，否则发货后销售额「消失」）

当前 `PAID_STATUSES = (PAID, COMPLETED)`。插入 `shipped` 后必须改为：

`(PAID, SHIPPED, COMPLETED)`

畅销、今日实收、成交单同步。`shipped` 已收款未签收，不算未支付。

储值图的 `recharge` 已按 `StoreRecord.kind` 汇总，自助充值成功后**自动进入**，不必新图表。可选：KPI 增加「待发货数」（非必须）。

## 5. 权限设计

| 动作 | 会员前台 | 店员 Admin | 管理员 Admin |
| --- | --- | --- | --- |
| 选配送/自提、填本单地址 | 是 | 代客下单时随 `create_order_from_cart` 传入（若后台仍从购物车生成，表单需补字段；否则仅前台结算） | 同店员 |

| 自提核销 | 否（防店外自助） | 是 | 是 |
| 整单退款 | 否 | 否 | 是 |

## 7. 异常与边界

| 场景 | 处理 |
| --- | --- |
| 配送单地址空就发货 | `OrderError`，不改状态 |
| 自提单点发货 | 拒绝，提示走自提核销 |
| 配送单点自提核销 | 拒绝 |
| 重复发货 / 重复签收 | 状态校验失败 |
| 待支付点发货/签收 | 拒绝 |
| 已退款点签收 | 拒绝 |
| 配送中退款 | 允许（管理员）；库存回补；已出店不模拟追件 |
| 已签收退款 | 仍允许（现规则）；不自动改签收时间 |
| 他人订单签收 | 404 |
| 并发双点签收 | 行锁，后到者「仅配送中可签收」 |
| 充值金额 ≤0、非数字、> 2000 | 表单错。上限 2000 为演示防乱填 |
| 已有待入账再开新单 | 拒绝 |
| 充值失败 | 写失败痕迹（本表 `trade_no`/`remark` 或次数 **不确定记法**，默认覆盖 remark「模拟失败」），状态仍 pending |
| 充值成功后重放 | 仅 pending 可付 |
| 充值超时后点成功 | 先扫后付，已关闭则拒绝 |
| 游客充值 | `member_required` → 登录 |
| 店员打开 `/member/recharge/` | 现装饰器会拒非会员 |
| 管理员后台与自助同时入金 | 都走 `apply_store` 行锁，余额不会负 |
| 支付花单储值不足 | **仍不拒单**，网关补足（承认第 13 条） |

配送超时自动签收：**不做**（无 Celery，也不该静默替会员签收）。

## 10. 风险与回滚

| 风险 | 可能后果 | 缓解 | 回滚 |
| --- | --- | --- | --- |
| `completed` 改义 | 论文/旧截图写「已完成」 | 中文统一「已签收」；旧图重录或口头说明 | 迁移可逆：label 改回，`shipped` 单改回 `paid` |

## 12. 需要你确认的问题（10 条）

1. **是否同意把 `completed` 改义为「已签收」，并插入 `shipped`？** 若必须「已完成之后再配送」，状态会叠床架屋，不推荐。
2. **是否做自提捷径？** 默认做。不做则所有单强制填地址。
3. **已支付未发货能否改地址？** 默认不能。
4. **会员能否在前台点「我已自提」？** 默认不能，仅店员核销。
5. **配送中是否允许管理员退款？** 默认允许，不模拟退货物流。
6. **充值是否赠积分或赠金？** 默认不赠。
7. **充值上限 2000 元是否可接受？** 仅防演示乱填。
8. **店员是否可见充值单 Admin？** 默认不可见。
9. **后台「从购物车生成订单」默认自提，是否可接受？** 否则要给 Admin 加地址表单（扩大）。
10. **历史已完成单按「自提已核销」回填，是否可接受？** 演示库可用 `seed_demo --force` 重建。

## 13. 各角色补充意见（实施时对照）

**产品**：一笔配送单现场演示路径 = 结算选配送 → 模拟支付 → 店员发货 → 会员签收。一笔充值 = 会员中心 → 100 元 → 模拟成功 → 流水出现 → 再下一单勾选优先储值。不要现场演示拒收。

**架构**：禁止把充值做成 `Order(goods_amount=0)`。禁止为轨迹引入新 app。`complete_order` 不要留一个「万能跳终点」的后门。

**库表**：`hold_key` 继续用可空唯一，兼容 MySQL 多 NULL。不要上部分索引。

**后端**：发货生成运单号放服务层，不要模板里拼。超时充值用 `update(status=closed, hold_key=None)`，对标过期券。

**UI**：窄屏结算先履约再金额；签收按钮不要和「模拟支付」并排以免点错。

**测试**：`shipped` 计入销售额的用例比美化运单号更重要。

**答辩老师会追问**：运费呢？轨迹呢？充值到账时间？——标准答：题目不接第三方；运费含在商品演示价里（若被追问运费，**不确定**是否要加运费字段，默认不加，口答「演示价已含送达」）。
